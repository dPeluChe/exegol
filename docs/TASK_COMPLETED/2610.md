## 2026-10-08: Faster reattach and no garbled first frame (branch `perf/reattach-repaint`)

- [x] Why: user log (packaged, 27 live sessions) `done 27 in 32888ms`, one session every 1-2 s
  even with 3 workers, and the active Claude Code pane showed a garbled frame after the reload
- [x] Measured with a local harness (real `SidecarClient` + `PtyHost` over a unix socket, fake
  sidecar answering `session.snapshot`; 18 x 8 MB coloured TUI rings + 9 x 1 MB shells, pool of
  3): 56.9 s total, ~3 s per 8 MB session, and nearly all of it in the snapshot fetch, not the
  xterm parse (~135 ms). Cause: `lib/ndjson` appends each socket chunk to one string and its
  `indexOf` flattens that string every time; macOS delivers unix socket data in 8 KB reads, so a
  12 MB snapshot frame is ~1,400 chunks and a quadratic copy (1.2 s for an 11 MB frame in a
  micro bench, 0.18 s in 64 KB chunks). Main-thread CPU, so the 3 workers serialized
- [x] Fix: `terminal/frame-buffer.ts` (now `lib/frame-reader.ts`), used by `pty-sidecar-client`: scans each chunk once
  for the newline and joins a frame once. `lib/ndjson` is bundled by the sidecar, so it stays
  (no SIDECAR_VERSION bump); its fix is noted in TASK_TODO T185.8
- [x] After: 4.6 s total for the same 27 (12x); per 8 MB ring fetch ~150 ms + parse ~135 ms, per
  1 MB shell ~20 ms parse; longest main-thread block ~250 ms. Lazy or chunked parsing was not
  needed: the parse is ~4 s of the remaining total and the pool keeps the panes' order
- [x] `[Reattach] OK` lines now carry `fetch Nms, N KB, parse Nms` per session
- [x] Garbled first frame: the ring is parsed at the stored grid and a pane's size is applied
  after it. A resize that arrived mid-replay resized the model while the rest of the ring was
  still being parsed; it is now held in `pendingSizes` until the parse ends. When the pane's size
  differs from the stored grid and the session is a TUI (not a plain shell, or on the alternate
  screen), `awaitsRepaint` (`terminal/reattach-repaint.ts`) holds the session's "ready" (so the
  "Reconnecting…" overlay and its snapshot) until the CLI's output after the resize pauses for
  120 ms, capped at 1.5 s; the pool does not wait for it. Logged as `[Reattach] repainted <id> in Nms`
- [x] Tests: frame-buffer (split frames, multibyte, malformed, overflow, 12 MB in 8 KB chunks
  under 1 s), `awaitsRepaint` decisions, PtyHost: resize mid-replay held, repaint wait ends on a
  quiet gap, cap, no wait for shells or the same size
- [x] Simplify: the reader moved to `lib/frame-reader.ts` and the MCP server, shim and claim guard
  read with it too (MCP is not in the sidecar bundle; `lib/ndjson` is untouched, now sidecar
  only). A test feeds random chunkings (split UTF-8, CRLF, blank lines, oversize frames) to both
  readers and expects the same frames. The reattach "done" (and the crash sweep after it) no
  longer waits for TUI repaints: `holdForRepaint` keeps that session's readiness past
  `settleAllReattach`, and `isSessionReconnecting` keeps its overlay after recovery is done
