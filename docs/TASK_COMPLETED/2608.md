## 2026-08-13: T176 — A quit that actually quits (PR #105)

Closing needed `kill -9`, and an orphaned sidecar from an earlier run survived alongside
the current one. Three separate causes; only the first was the one being looked for.

- **Electron does not quit on SIGTERM.** No handler existed, so the signal was ignored
  outright. `installSignalHandlers` now asks for a normal quit and force-exits after 8s —
  and the forced path runs teardown first, since `app.exit()` emits neither `before-quit`
  nor `will-quit` and would otherwise leave the database open.
- **Teardown was a straight line of sync calls**, so a step that threw skipped every step
  after it, `closeDatabase()` included. Steps are now isolated, named and timed; the log
  says which one is slow instead of us reading a process tree. `markShutdown` moved to
  LAST — it silences console output, so running it first hid every `[Shutdown]` line.
- **The orphaned sidecar had its own root cause**, found in review: a shutting-down sidecar
  unlinked the socket and pid file unconditionally, and discovery spawned the replacement
  without waiting. The old process, exiting ~500ms later, deleted the NEW sidecar's files —
  it kept serving on an unlinked inode with no pid file, so the next launch found nothing,
  spawned a third, and left the second holding the previous run's PTYs. `cleanup()` now
  removes only files this process owns; discovery waits for the predecessor (escalating to
  SIGKILL) before spawning. `SIDECAR_VERSION` → 1.4.0.

Reviewers killed two things that looked right: a teardown deadline that could never fire
(a timer cannot interrupt the synchronous loop it wraps — the deadline now lives only in
the signal handler, where `app.quit()` returns immediately), and a 500-file cap on the
hook-event sweep that would have traded a slow quit for an unbounded disk leak, since
`cleanupOldEvents` prunes a DB table rather than that directory. The sweep moved to
startup, uncapped, off the quit path entirely.

## 2026-08-16: T175.1 — Path claims become enforceable, not just polite

Claims were advisory *and* unobservable: in a shared working tree git cannot attribute a
change to an agent, so by the time a file is dirty "who did it" is gone. The first design
— diff the tree at each turn boundary and compare touched paths — was dropped for exactly
that reason: it can detect that a claimed file changed, never who changed it.

The one moment attribution is certain is **before** the write, inside the tool call. So
enforcement is a Claude Code `PreToolUse` hook (`exegol-claim-guard-bin.ts`) that asks the
app over the existing MCP socket with a new `check_path` method, and exits 2 with an
explanation on stderr when the path is held by another live agent. The model is told to
pick another file or agree a handover via `agent_send`; the user hears it through a
NotificationBus `agent:attention` event, so a collision is not buried in a ring buffer.

Design constraints that shaped it:

- **Fails open on every uncertainty** — no socket, no token, no answer, unparseable
  payload, ambiguous identity, and now a 3s self-deadline. A guard that blocks when it
  cannot reach the app would stop an agent working across an app restart, which is worse
  than a missed collision.
- **Identity is never claimed by the caller.** The guard sends only the per-agent token
  from its PTY env; the server derives the agent from it. It deliberately does *not* fall
  back to `<cwd>/.mcp.json` the way the shim does — in a shared repo that file holds a
  sibling's token, which would make the guard ask under another agent's identity.
- **Only where it can collide.** `enforceClaims` follows `!useWorktree`: an agent alone in
  its own worktree pays no guard spawn per write.

Review removed the costs that would have scaled with the fleet: the guard no longer sends
`ppid` (resolving it cost the *main* process three synchronous `ps` forks per write, and
buys nothing when the token is already per-agent), guard connections are no longer
announced into the 100-entry MCP activity ring (~33 edits would have evicted every real
agent call from the panel), and the hook matcher is anchored so an MCP tool merely
*containing* "Write" no longer pays a process spawn.

## 2026-08-16: T170.1 — Delivery state that survives the process

`message_status` answered from a `Map`. So the moment the app restarted, every message
became `unknown` to its sender, and a retry carrying the same `client_key` — the retry the
tool exists to make safe — delivered a second copy. Both failures land exactly when a
sender most needs the answer.

State now lives on the `messages` row (`delivery_state`, `delivered_at`, `client_key`, with
a partial unique index on `(from_agent_id, client_key)`), so idempotency is a database
constraint rather than a lookup a process death forgets, and the sender-scoping that used to
be a `${agentId}:` string prefix is the index itself.

Two things deliberately did NOT move:

- **The live queue stays authoritative for queued-vs-delivered.** Storing that twice is how
  `agent_send` once answered "queued" for a message `message_status` called "delivered" —
  the two tools disagreeing in the one case they exist for. The row answers for everything
  else, which is what survives a restart.
- **The 30-second content dedup stays in memory.** It guards against a model sending the
  same sentence twice in a row; it was never a durability promise.

A startup sweep marks anything still `queued` as undeliverable, which is simply true: the
queue that would have delivered it died with the process. A sender gets an answer instead
of waiting on a message that exists nowhere.

Review pushed the change one level deeper. The messaging module reached for `getDb()` even
though `sendAgentMessage` already receives a `db` — proven by the test having to mock a
process global while also passing a database explicitly, giving the suite two routes to one
database that only agree by luck. `db` is now a parameter on every messaging entry point
(`deliverPendingAgentMessages`, `getMessageDeliveryState`, `cancelQueuedMessage`,
`clearAgentMessageQueue`); the single remaining ambient lookup is the 2s quiescence timer,
which has no caller to thread one from.

Also from review: the redundant `trackMessage` UPDATE went away (the INSERT already wrote
`queued`), a dropped queue is one statement instead of ten, the sweep is indexed
(`messages` rows are never deleted, so a full scan would get slower every release) and it
moved into `runStartupRecovery` ahead of the reattach — it is a reconciliation whose
correctness depends on running before any queue exists, which `cleanupStaleData` did not
say. `delivered_at` was dropped for having no reader.

Items 2 (generalize idempotency to the RPC layer) and 3 (tokenless config) stay on the
board — the first is explicitly "build it when the SECOND tool needs it", the second needs
two live sessions of one provider to verify per CLI.

## 2026-08-16: T166.1 — The MCP surface stops trusting its inputs

Three uncapped inputs and a warning nobody could see.

**A newline-less flood had no ceiling.** `createNdjsonBuffer` appended every chunk until it
found a newline, in the main process — so a client that never sent one grew the buffer until
the app died, taking every PTY with it. There is now an 8 MB frame limit: on overflow the
buffer is discarded up to the next newline (resuming mid-message would parse garbage), the
incident is reported once rather than once per chunk, and the connection recovers as soon as
a valid message arrives instead of being dropped.

**`memory_save.fact` and `memory_search.query` were the only uncapped tool inputs** —
`agent_send` has been capped since T157. A fact is one sentence by design and a query is a
phrase; 4 000 and 500 characters sit far above real use and below "an agent pasted a file
into the memory store". Review moved both caps down to `memory/store.ts`, where `agent_send`
enforces its own: at the MCP door they would have held only for agents, while the extractor
— the highest-volume writer — walked straight past. The tool schemas now declare the same
limits as `maxLength`, so the model reads the constraint instead of learning it from a
rejection.

**The credential warning became a notification.** `warnIfCommittable` fires when a config
holding a live MCP token is not gitignored — and it was a log line nobody reads, for a
credential in the user's repo. It now emits `security:warning` on the NotificationBus, and
that type is deliberately absent from `muteChannelForEvent`: muting it silently is the one
outcome that costs the user something they cannot undo.

Review also found the same unbounded framing loop in `pty-sidecar-client.ts` — on a socket
that carries far more traffic, in the same main process, and still missing the multibyte
decoder fix. It consumes `createNdjsonBuffer` now, so the cap and the decoder are genuinely
in one place. (`pty-sidecar-entry.ts` has a third copy; fixing it means bumping
`SIDECAR_VERSION`, which kills every live PTY, so it stays on the board.)

The T166 bullet asking Exegol to **gitignore those files itself was dropped**, not
implemented: T173 settled that they are legitimate project config a team may want versioned,
and Exegol only inserts the `exegol` key. Telling the human is the correct end of that
decision.

## 2026-08-16: T179.3 — Run actions: Makefile, justfile, and actions you wrote down

Script detection knew npm/bun, Python, Cargo and Go — so a repo whose entry point is `make
dev` showed an empty Dev Scripts row. Three sources added, as a complement to the existing
inference rather than a replacement for it: `Makefile` targets, `justfile` recipes, and
`.exegol/actions.yaml` (`name: command`, the same line-based shape as `lifecycle.yaml`).

What the parsers deliberately reject is most of the work: `.PHONY`, `%` pattern rules,
`VAR := value` assignments and indented lines all look like targets and none of them are.
A false positive here is a button that runs something meaningless.

A Makefile can carry sixty targets and the launcher renders every script it is handed, so
detected targets are ranked by what a person actually runs (dev, run, build, test, lint, …)
and capped at twelve per file. Custom actions come last and are never truncated: someone
wrote them down on purpose, which beats any heuristic above them.

The chips name the runner (`make`, `just`, `custom`) rather than the file, and only when it
is not the default one — `build` from `package.json` and `build` from a Makefile are
different commands with one label, but tagging every npm script `(package.json)` would be
noise. The full command is in the tooltip either way.

Review caught the thing that mattered: **these are commands read out of a repo**, and they
were the only such commands not passing `security/command-guard` — a clone could put
`rm -rf ~` behind a chip labelled "dev", and the chip shows only the name. They go through
the same gate as lifecycle hooks now. While testing that, the guard's own `rm -rf ~` pattern
turned out not to match `rm -rf ~/` — the way a person actually types it — so that is fixed
too.

It also found the third copy of the `key: value` loop (lifecycle, project hooks, run
actions), already drifted: only one stripped trailing comments, so `seed: bun run seed #
dev only` executed the comment. One `lib/flat-config.ts` now serves them. And detection —
~20 stats on the main thread, in the default state of every new pane — is behind a 60s TTL
cache.

## 2026-08-18: T181 — Session history per repo, from both sides

"Se ven las sesiones abiertas, pero ¿y las cerradas? ¿y las que corriste con otros agentes?"
(Antonio). The answer had two failures underneath it, and the first was self-inflicted.

**We were deleting the history.** `cleanupStaleData` ran on every startup and dropped every
`completed | failed | stopped` session older than a day and every `crashed` one older than an
hour — and that DELETE cascades into `agent_scores`, `token_usage`, `oplog` and
`host_metrics`. So the score, the spend and the operation log went with the row. No view
could have answered the question; there was nothing left to read past 24 hours. Agent
sessions are kept now. Shells stay ephemeral: no task, no score, no memory — they are
terminal tabs, not sessions.

**Exegol only ever knew its own sessions.** Every CLI keeps a local store keyed by working
directory, so everything the user ran in a plain terminal was invisible to us — for a tool
whose job is orchestrating those CLIs, most of the truth. Three adapters, each verified
against the real store on this machine:

| Provider | Store | Carries |
|---|---|---|
| claude-code | `~/.claude/projects/<cwd-slug>/*.jsonl` | AI title, git branch, CLI version, start time |
| codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` | session id, cwd, branch, CLI version |
| opencode | `~/.local/share/opencode/storage/session/*/ses_*.json` | title, directory, created/updated |

Two bugs that only a real store could have shown, both silent:

- Claude Code slugs a cwd by replacing **`/` and `_`** with `-`, so `/…/_code_/labs-exegol`
  lives under `…--code--labs-exegol`. Slugging only `/` looked in a directory that does not
  exist and reported zero sessions for a repo that had them. That encoding is also lossy, so
  the transcript's own `cwd` field is what decides the match now — the slug only says where
  to look.
- codex's `session_meta` line embeds the model's full `base_instructions` and runs 15–22 KB.
  Reading a short head truncated the line, `JSON.parse` failed, and every codex session
  vanished without an error.

Both are locked in by tests written from the real shapes, not from guesses.

**What the merge refuses to do** is as important as what it does. An Exegol-launched claude
session lives in both stores; where the captured provider session id proves they are the
same, the Exegol row wins, because it carries the score, the spend and the oplog that the
file cannot. And a local session gets `status: null`, `score: null`, `cost: 0` — a store on
disk records that a session happened, never how it went, and inventing an outcome would make
the two sources indistinguishable. The UI labels those rows `outside Exegol`.

Sessions also keep the tail of what they last said (`final_output`, 16 KB, ANSI-stripped at
exit): a score with no output is a number nobody can check, and the ring buffer dies with the
process.

The base view is the last 30 days, per Antonio: everything older stays, reachable through the
range filter, "para referencia únicamente".

### What the simplify round changed

The review pass caught a bug the feature would have shipped with: **the dedupe key was
claude-only**. `claude_session_id` is written by the status parser only for claude-code, so
every codex or opencode session Exegol launched would have appeared twice — once with its
score, once labelled "outside Exegol". `resume_command` is captured for every provider and
contains the id, with the prefix already declared as `capabilities.resumeCommandPattern`, so
`providerSessionId()` derives it generically at read time — no migration, and existing rows
benefit.

Measured costs removed:

- The scan cache keyed on `since`, which is derived from `Date.now()` — so the key changed
  every second, the cache never hit on any range but "All", and the map grew an entry per
  request-second forever. Keyed on `days` now, through the existing bounded `AsyncLruCache`
  (which also collapses two panes mounting at once into one scan).
- The history query sorted and aggregated over every matching session before paginating:
  44 ms → 2 ms on a 5 000-session database, and it no longer scales with history size — which
  matters precisely because sessions are no longer purged. Filter, sort and LIMIT now happen
  in a CTE and the aggregates hang off the page.
- The codex adapter opened and parsed all 756 rollouts sequentially, ~6 MB of JSON, to keep a
  handful. Bounded concurrency, a substring reject on the raw line before the 20 KB parse, and
  one open per file instead of two: 137 ms → 36 ms over the full ten-year window.
- Clicking a provider chip rescanned every CLI's store, for a facet over data already in hand.
  It is a client-side filter now.

Reuse the review found: `FilterChip`, `formatTokens`/`formatCost`, `formatDuration` (the
fourth copy of "Xh Ym" — now shared), and `ScoreBadge` (extracted so the same score does not
read as a badge in Scoring and a raw decimal in History). The status colour was using
`text-danger`, which is not a token in this codebase — failed sessions rendered uncoloured;
it goes through `statusToSemantic` now.

Left on the board, all the same shape — provider knowledge accumulating outside the provider
registry, and "what is a session" re-decided per call site: `configDir`/`localHistory` as
provider capabilities, one retention policy instead of three, and an `isShellAgent` helper.

743 tests pass.

## 2026-08-19: Round-9 code review — what it caught, and what it fixed

Four agents over `eb6b37e..HEAD` (six merged PRs, 75 files), each with a correctness mandate
— the simplify passes that ran per-PR deliberately exclude correctness, so this was the gap.
Everything below was confirmed by execution against real data, not by reading.

**Two regressions this wave introduced, both silent:**

- **The 8 MB NDJSON frame cap was smaller than the largest legitimate frame on the sidecar
  socket.** `session.snapshot` answers with the whole ring buffer in one line, and JSON
  escaping inflates an escape byte to six characters. Measured: 8 MB of coloured output
  serializes to 10.7 M chars against a ceiling of 8.4 M. The reply would be discarded,
  `snapshot()` would hit its 10 s timeout, the `catch {}` above it would swallow that, and a
  reattached terminal would come back **blank** — precisely what the ring buffer exists to
  prevent, for every agent with more than ~7 MB of output. The ceiling is per-channel now:
  the MCP socket keeps 8 M, the sidecar gets `RING_BUFFER_CAPACITY * 4`.
- **Archiving a session blanked its still-open terminal pane.** `archiveOne` removed the
  agent from the store, and `WorkspacePane` reads "terminal status + not in store" as a
  leftover from a previous session and rewrites the pane to the launcher grid. Tidying the
  dashboard destroyed the transcript, with no undo, and "Archive all" did it to every ended
  pane at once. Archiving flags the row now instead of removing it.

**And the one that mattered most — T181's retention was defeated by the most-travelled path.**

## 2026-08-19: Pre-DMG — the two things that only matter once it is installed

Before packaging, two fixes whose absence would have shown up as noise or silence in the
installed app rather than in dev.

**A locally built app would have reported a broken updater forever.** The feed points at
`releases/latest/download` on the GitHub repo, and there are no releases published — so every
check, at launch and every four hours, answers 404. A 404 is not in the silenced set, so it
surfaced as a user-facing error status about something the user cannot act on. "Nothing has
been published yet" is now its own outcome: logged, reported idle.

**T182·2, claims through symlinked paths — shipped.** macOS makes this the default case
rather than an edge one: `/tmp` is a symlink to `/private/tmp` and `/var` to `/private/var`.
A claim stored one way and a guard asking the other never overlap, so enforcement did nothing
at all for that project, with no signal anywhere. Both sides go through `realpathSafeSync`
now — stored claims in `resolveAgentPaths`, the guard's question in `check_path`. The
existing tools test caught it immediately by failing on `/var` vs `/private/var`, which is
the bug stated as a diff.

One trap avoided while writing it: resolving the base before checking it exists would have
made `realpath("")` return the MAIN PROCESS's cwd, silently anchoring every claim there
instead of refusing. The check stays ahead of the resolve.

Also verified for the package, since these only break once bundled: `ELECTRON_RUN_AS_NODE`
does execute a script from inside the asar (tested against a real asar), so the MCP shim and
the claim guard work without being unpacked; the entitlements carry
`disable-library-validation` and `allow-unsigned-executable-memory`, which is what node-pty,
libsql and the detached sidecar need; and `pty-sidecar-entry.js` is in `asarUnpack`.
