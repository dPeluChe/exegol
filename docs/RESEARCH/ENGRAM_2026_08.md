## Veredicto vs Exegol

- **Retrieval/decay: vamos adelante** (su FTS5-only + review_after fijo < nuestro RRF híbrido
  + salience v2). **Seguridad: vamos adelante** (su HTTP localhost SIN auth vs nuestro socket
  + tokens). NO regresionar.
- **Hábito de memoria: van MUY adelante** — el modelo usa la memoria sin que se lo pidan,
  vía un stack de 5 capas redundantes. Es la respuesta a nuestra pregunta abierta.

## El stack de inducción de hábito (a portar — T158)

1. **Server instructions del MCP**: "PROACTIVE SAVE RULE: mem_save inmediatamente tras
   CUALQUIER decisión — no solo cuando te lo pidan" + protocolo de conflictos.
2. **Registro declarativo por provider** (`internal/setup/agents.go`): un protocolo canónico
   + por CLI `{mcpConfigPath, mcpFormat, instructionPath, markerBlock}` escrito como managed
   block en el rules file NATIVO de cada CLI (~/.gemini/GEMINI.md, AGENTS.md, etc.) — así
   cubres CLIs sin hooks. Mapea 1:1 a nuestro registry + writer de managed blocks (T140).
3. **Inyección al session-start** (hooks): trigger-list de guardado ("usuario confirma tu
   recomendación", "usuario rechaza un enfoque"), **self-check** ("¿acabamos de decidir algo?
   → mem_save AHORA"), triggers de búsqueda ("primer mensaje referencia el proyecto →
   mem_search antes de responder"), y summary de sesión obligatorio antes de decir "done".
4. **Nudge temporizado con debounce**: cada mensaje del usuario, si sesión >5min y último
   save >15min → inyecta "MEMORY REMINDER"; cooldown de 15min para no ser pesado. Exegol:
   entregarlo en turn boundary (señal Stop de T123) desde el main process — sin bash frágil.
5. **Contrato post-compactación**: pasos numerados obligatorios (persistir summary → recall
   → recién entonces continuar). + SubagentStop → extracción de "## Key Learnings".

## Para el memory store (mejoras puntuales)

- **`topic_key` upsert**: decisiones evolutivas = UNA fila actualizada in place
  (revision_count++), no N casi-duplicados compitiendo en recall. Columna + upsert +
  `suggest_topic_key`.
- **Conflicto con agente-como-juez**: `memory_save` → `judgment_required + candidates[]` →
  `memory_judge(relation, reason, evidence, confidence)`; umbral explícito: confidence <0.7
  o supersedes/conflicts en tipos decision/architecture → **preguntar al usuario**; resto
  silencioso. Verdicts persistidos con provenance (qué modelo juzgó, evidencia = palabras
  del usuario). Mejora nuestro supersede transaccional en el caso ambiguo.
- Dedup write-time por hash normalizado + ventana → duplicate_count++ (refuerzo implícito).
